> 来源：逆向 `com.yl.milight` v1.0.0（内部包名 `com.lenzetech.colorfulled`，ColorfulLED）
> 方法：静态反汇编（自研 DEX 解码器）+ 常量帧比对验证
> 状态：**框架与校验和已用 App 内置常量帧 100% 验证**；参数语义由 UI 调用点反推，标注了置信度

## 1. GATT 层

| 角色 | UUID | 说明 |
|---|---|---|
| Service | `0000FFB0-0000-1000-8000-00805F9B34FB` | 主服务 |
| Characteristic (写入) | `0000FFB1-0000-1000-8000-00805F9B34FB` | **Write Without Response** |
| Characteristic (通知) | `0000FFB2-0000-1000-8000-00805F9B34FB` | Notify |
| Descriptor | `00002902-0000-1000-8000-00805F9B34FB` | CCCD |

APK 中还存在 `FFF0` / `FFF3` 两个 UUID 字符串，但在**所有实际收发路径上未被使用**（推测为兼容其它型号固件的备选，或第三方库默认值残留）。新版本建议做成「候选 UUID 列表 + 自动探测」而不是硬编码单一值。

### 连接参数（照抄原 App）

```
扫描：searchBluetoothLeDevice(timeout = 7000 ms, retry = 1)
连接：connectRetry = 3, connectTimeout = 30000 ms
服务发现：serviceDiscoverRetry = 3, serviceDiscoverTimeout = 20000 ms
```

### 连接建立后的握手

```
1. enableNotify(FFB0 / FFB2)
2. write(FFB1, "55 01 00 FE AA")   # 查询设备信息
3. 收到 "55 0E 00 ..." 状态帧 → 刷新 UI
```

断线处理（原 App 行为）：收到 status=32（disconnected）时，**只要蓝牙仍开启就立即重连**，无退避延时。新版务必加指数退避，否则会形成重连风暴。

## 2. 帧结构（0x55 家族，主协议）

```
+--------+--------+--------+----------------------+--------+--------+
|  0x55  |   L    |  CMD   |  PAYLOAD (L-1 字节)  |   CK   |  0xAA  |
+--------+--------+--------+----------------------+--------+--------+
   1字节    1字节    1字节         L-1 字节          1字节    1字节
```

* `L = 1 + len(PAYLOAD)`（CMD 自身占 1）
* **帧总长 = L + 4**
* `CK = (~(L + CMD + Σ PAYLOAD)) & 0xFF`
  （等价于：从下标 1 到 CK 前一个字节全部相加，取反加 1 后的低 8 位；即 `0x100 - sum`）

> 校验和的三个「已知明文」验证点（App 里以常量数组硬编码，校验位也是常量，可直接对照）：
>
> | 帧 | 求和范围 | 计算 | 结果 |
> |---|---|---|---|
> | `55 01 00 ?? AA` | 01+00=01 | ~01 | **FE** ✓ |
> | `55 02 16 01 ?? AA` | 02+16+01=19 | ~19 | **E6** ✓ |
> | `55 02 16 03 ?? AA` | 02+16+03=1B | ~1B | **E4** ✓ |

反例（勿用其它规则）：
* 不是 `Σ` 取低 8 位（那是 `19` 不是 `E6`）
* 不是 `0x55 + ...`（0x55 不参与求和）

## 3. 命令一览（上位机 → 设备）

| CMD | 名称 | PAYLOAD | 取值 | 完整帧示例 |
|:--:|---|---|---|---|
| `0x00` | 查询设备信息 | — | — | `55 01 00 FE AA` |
| `0x02` | 双区亮度 | `b1 b2` | 0–100 | `55 03 02 64 64 32 AA`（100/100） |
| `0x03` | 模式设置 | `p1 p2` | 见 §3.3 | `55 03 03 01 02 F6 AA` |
| `0x04` | 双区 RGB | `r1 g1 b1 r2 g2 b2` | 0–255 | `55 07 04 FF 00 00 00 00 FF F6 AA` |
| `0x05` | 开关 / 跟随 | `p` | 0=关 1=跟随 2=开 | `55 02 05 02 F6 AA`（开） |
| `0x06` | 声音灵敏度 | `v` | 0–100 | `55 02 06 32 C5 AA`（50） |
| `0x10` | 查询状态 A | `00` | — | `55 02 10 00 ED AA` |
| `0x11` | 查询状态 B | `00` | — | `55 02 11 00 EC AA` |
| `0x12` | 查询状态 C | `00` | — | `55 02 12 00 EB AA` |
| `0x16` | 系统指令 | `p` | 01=内置模式 03=RF 配对 | `55 02 16 01 E6 AA` |
| `0x22` | 流水模式 | `(v-1)<<4 \| (m+10)` | m:0–4, v:1–16 | `55 02 22 2A B1 AA` |
| `0x23` | 速度 | `v` | 0–5 | `55 02 23 03 D7 AA` |
| `0x24` | 方向 | `v` | 0=正向 1=反向 | `55 02 24 01 D8 AA` |
| `0x25` | 转向跟随 | `v` | 0/1（1=跟随；原 App 界面默认 0） | `55 02 25 01 D7 AA` |
| `0x26` | 灯珠数量 | `v` | 0–150 | `55 02 26 96 41 AA`（150） |

### 3.1 `0x02` 双区亮度

```
55 03 02 b1 b2 CK AA      b1 = 分区1 亮度(0..100), b2 = 分区2 亮度(0..100)
```
原 App 的亮度 SeekBar `max=100, progress=64`，直接把 `getProgress()` 强转 byte 下发。
「全区控制」模式下 b1 = b2 = 同一个值。

### 3.2 `0x04` 双区 RGB

```
55 07 04 r1 g1 b1 r2 g2 b2 CK AA
```
顺序确认无疑（`BLE_RGB_CHANGE(int r1,int g1,int b1,int r2,int g2,int b2)` 顺序写入 buf[3..8]）。
分区模式（分区1 / 分区2 / 全区）决定哪些字段被更新；全区时 6 个字节写同一颜色。

> 注意：原 App 的 `BLE_RGB_CHANGE` 在「6 个参数全为 0」时**直接 return 不发包**，所以纯黑无法通过 RGB 命令表达——要关灯请用 `0x05` payload=0。

### 3.3 `0x03` 模式设置

`55 03 03 p1 p2 CK AA`。`p1/p2` 语义未完全确定（置信度中）：
原 App 只有两个调用点——音乐页 RadioGroup 与模式选择列表——传的是列表项索引相关值。
**新版建议**：先按枚举透传，用真机逐项抓包建立映射表，不要猜。

### 3.4 `0x22` 流水模式（位域打包）

```c
payload = ((value - 1) << 4) | (familyIndex + 10)
```

* `familyIndex`：0–4（0 基），对应界面 5 个模式族
  （`七彩 / 幻彩 / 魔幻 / 律动 / 跟随`），低半字节因此为 `0x0A..0x0E`
* `value`：1–16，该族下的档位（`七彩-1 … 七彩-6` 等）

例：`familyIndex=0`（七彩）、`value=3` → `((3-1)<<4)|(0+10)` = `0x20|0x0A` = **0x2A**
→ 完整帧 `55 02 22 2A B1 AA`

> 代码里 `familyIndex` 的求法是「把下发的模式名与资源字符串数组逐个 `equals`，命中则 `i+10`」，
> 未命中时 `v0=0`（即低半字节 0），属于原 App 的 bug 边界。

### 3.5 `0x05` 开关的三态（易错）

| 值 | UI 文案 | 含义 |
|:--:|---|---|
| 0 | 关闭 | 关灯 |
| 1 | 跟随 | 跟随（音乐/麦克风律动） |
| 2 | 开启 | 常亮 |

UI 单选「开启/关闭/跟随」的顺序与取值是 **2 / 0 / 1**，并非 0/1/2 —— 移植时极易写错。

## 4. 状态上报（设备 → 上位机）

### 4.1 全量状态帧（18 字节）

```
55 0E 00 | 13 字节状态 | CK AA
 ^  ^  ^
 |  |  +-- 状态类型 0x00 = 全量状态
 |  +----- L = 0x0E = 14 = 1 + 13
 +-------- SOF
```

PAYLOAD 布局（PAYLOAD[i] = 帧内 buf[3+i]）：

| i | 含义 | 范围 |
|:--:|---|---|
| 0 | 分区1 亮度 | 0–100 |
| 1 | 分区1 模式 | — |
| 2 | 分区1 R | 0–255 |
| 3 | 分区1 G | 0–255 |
| 4 | 分区1 B | 0–255 |
| 5 | 分区2 亮度 | 0–100 |
| 6 | 分区2 模式 | — |
| 7 | 分区2 R | 0–255 |
| 8 | 分区2 G | 0–255 |
| 9 | 分区2 B | 0–255 |
| 10 | 开关 | 0=关，非0=开 |
| 11 | 麦克风电平 | 0–255 |
| 12 | 未使用/未知 | — |

实测样例（构造，用于自测）：
`55 0E 00 50 03 FF 00 00 28 05 00 00 FF 01 20 00 52 AA`
→ 分区1(亮度80, 模式3, 红) / 分区2(亮度40, 模式5, 蓝) / 开 / 麦克风32

### 4.2 其它状态类型（同 `0x55` 家族）

响应帧的 CMD 字节被当作「状态类型」使用，App 用 `packed-switch` 分派：

| 类型 | 处理 | 载荷 |
|---|---|---|
| `0x00` | 全量状态（§4.1） | 13 字节二进制 |
| 其它 | **ASCII 文本**，`new String(bytes)` 后**去掉最后 1 字节** | 变长 |

ASCII 类的字段在 App 中的用途：

| 日志/字段 | 含义 |
|---|---|
| `DEVICE_VERSION` | 固件版本 |
| `DEVICE_MODEL` | 设备型号 |
| `DEVICE_STATE` | 工作状态 |
| 车辆状态 / 年款 / 车架号 | 车灯型号相关（原 App 遗留，氛围灯用不到） |

> 复刻要点：`new String(bytes)` 用**平台默认字符集**（非 UTF-8 显式指定），且 `substring(0, len-1)` 砍掉末字节。
> 新版请显式 `UTF-8` + 按 NUL 截断，并在长度不足时容错。

## 5. 旧版协议（0x7E 家族）—— 摇一摇专用

`hearShake()`（摇一摇换色）**不走** `0x55` 协议，而是直接写死 9 字节的旧帧：

| 动作 | 帧 |
|---|---|
| 关灯 | `7E 04 04 00 00 00 FF 00 EF` |
| 白光 | `7E 04 04 00 00 01 FF 00 EF` |
| 七彩闪 | `7E 05 03 95 03 FF FF 00 EF` |
| （第 4 条） | `7E 07 05 03 FF FF FF FF EF` |

* 首字节 `0x7E`、末字节 `0xEF`，**无校验和**
* 第二字节看起来像长度/类型（04 / 05 / 07），但四帧长度都是 9 字节，不能当长度用
* 语义置信度：低。仅确认这 4 条固定帧，未找到通用编码规则

**新版建议**：摇一摇改为「软件侧随机取色 → 用 `0x04`/`0x05` 下发」，不再依赖这套未解码的旧帧；
若必须保留原行为，则原样透传这 4 条常量。

## 6. 写入策略与流控

原 App：`writeNoRsp` 逐条直发，**无队列、无去重、无节流**。
后果：滑动 SeekBar 时 `onStopTrackingTouch` 才发（还好），但摇一摇/音乐律动会高频连发，超过 BLE 每秒包数上限后固件可能丢包。

新版务必实现：

```kotlin
// 同一个 key 的写请求在 100ms 内合并，只发最后一次
class WriteThrottler(private val minIntervalMs: Long = 100) { ... }
```

推荐策略：
1. **合并（conflate）**：颜色/亮度滑动 → 只在「同一字段」上合并，保留最后一次
2. **串行队列**：单 worker，前一条 `onCharacteristicWrite` 回调后再发下一条
3. **命令短间隔**：`0x10/0x11/0x12` 三连查询至少间隔 500ms（原 App 用 500ms、1000ms 延时）
4. **MTU**：单帧最长 18 字节，默认 MTU 23（有效 20 字节）足够，**无需协商 MTU**
